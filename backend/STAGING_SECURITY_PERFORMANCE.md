# المرحلة 144 — أمن وأداء Staging

## نطاق الاختبار
الاختبارات تستخدم فقط بيانات اصطناعية في قواعد CI، ولا تستهدف Railway بطلبات ضغط. 1423 موظفًا اصطناعيًا و25 مركزًا، طلبات JWT فعلية، اختبار الأدوار المسموح بها والمرفوضة، المنع عبر المسارات المباشرة، رفض الرمز غير الصالح والطلبات الكبيرة، التحقق من سحب الاعتماد التنظيمي. 20 قراءة على PostgreSQL بحد أقصى 4 عمال في الاختبار المحلي؛ قياس p95 والزمن وعدد الاستعلامات، وليس اختبار تحمل الإنتاج.

## التحسينات
- استرجاع الحقول اللازمة فقط للتحقق من هوية الموظف الاصطناعي وعلاقته، دون جلب البطاقة الصحية أو جميع الحقول الشخصية عند عرض الدليل المحدود.
- حساب مسار الاعتماد مرة لكل وحدة في الطلب نفسه؛ لا تخزين للصلاحيات بين الطلبات.
- حد 12 استعلامًا لكل طلب دليل محدود في الاختبار، مع قياس الزمن (ليس SLA).
- حد 16 KiB لطلبات المصادقة ذات Content-Length المحدد، دون تغيير حدود رفع Excel.
- منع إعادة توجيه الطلبات الموثقة من واجهة Staging؛ رؤوس no-store وnosniff وno-referrer وDENY لاستجابات API.
- فحص تبعيات Python المثبتة وnpm في CI، تقارير فقط: الفشل أو غياب بيانات الفحص أو وجود نتائج يجب مراجعته منفصلًا قبل الجاهزية التشغيلية. لا تعني نتيجة CI الخضراء أن جميع التبعيات آمنة؛ الفحص لا يشمل كامل البنية التحتية أو اختبار اختراق احترافي.

## ضوابط التكلفة
إعادة استخدام مهام CI الأربع الحالية، دون قاعدة إضافية دائمة أو زيادة العمال/الذاكرة أو تغيير اشتراك Railway. القياسات تعكس بيئة CI فقط؛ الاستهلاك الفعلي وCPU والذاكرة وp95 في Railway غير مقاسة. يتطلب الاختبار الحي موافقة منفصلة وحدودًا وبيانات اصطناعية ونافذة مراقبة.

## متطلبات متبقية قبل الاعتماد
مراجعة نتائج التبعيات وإصلاحها، قياسات حية محكومة، تحقق مستقل من إعداد الأسرار وTLS وإدارة الجلسات وMFA، اختبار ميداني للأدوار والمرفقات والتقارير، نسخ Staging مستقلة واستعادة مثبتة. لا بيانات فعلية أو إطلاق Production.
