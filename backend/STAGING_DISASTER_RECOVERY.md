# خطة التعافي من الكوارث — المرحلة 143 (Staging فقط)

## نطاق التنفيذ
اختبار اصطناعي مستقل في PostgreSQL 18 على GitHub Actions، من دون الاتصال بقاعدة Railway أو إنشاء خدمة دائمة. الأداة الجديدة `ops/staging_disaster_drill.py` تقبل فقط عناوين loopback وأسماء قواعد الاختبار المحددة؛ لا تستخدمها مع قواعد فعلية أو أنفاق إلى Railway. تأكيد المشغّل بأن البيانات اصطناعية شرط، وليس تصنيفًا آليًا للبيانات.

- تشفير AES-256 بواسطة GnuPG؛ نسخة custom-format وبيان تحقق مشفر مستقل. حفظ مفتاح خارج مجلد النسخة والمستودع؛ لا نص واضح على القرص ولا أسرار أو بيانات شخصية في سجل الاختبار.
- لقطة PostgreSQL repeatable-read واحدة تُستخدم للبصمات وpg_dump. مقارنة عدد وبصمة محتوى كل جدول public عادي بعد الاستعادة؛ تشمل المرفقات الثنائية والبطاقة والتنظيم والمستخدمين وسجل التدقيق والجلسات. لا تثبت مطابقة كل كائنات قاعدة البيانات أو قيم التسلسلات أو الإعدادات الخارجية.
- الاستعادة لا تتصل بالمصدر، وتتحقق من تشفير البيان والنسخة والبصمة قبل استعادة قاعدة فارغة قابلة للتخلص منها؛ لا DROP أو --clean أو --create. اختبار مفتاح خاطئ، تعديل النسخة، إعادة الاستعادة، اسم المصدر، وعدم التأكيد.
- نتائج الاختبار تسجل عدد الجداول والصفوف وحجم النسخة المشفرة وزمن التنفيذ، ولا تنشر النسخ أو المفاتيح أو البصمات التفصيلية في GitHub. الأرشيف المؤقت يزال عند نهاية المهمة.
- الأداة السابقة `secure_pg_backup.py` لم تُغير؛ لا تعتبرها آمنة للاستعادة الحية. لا توجد نسخة مستقلة من Railway أو اختبار استعادة فعلية حتى الآن.

## أهداف مقترحة للاعتماد المؤسسي (ليست قياسات محققة)
| المؤشر | الهدف المقترح |
|---|---|
| RPO — أقصى فقد مقبول للبيانات | 24 ساعة |
| RTO — أقصى مدة لاستعادة الخدمة | 4 ساعات |
| النسخ المستقلة | يومية بعد الموافقة، خارج Railway |
| الاحتفاظ | 7 يومية + 4 أسبوعية مبدئيًا، حسب السياسة والميزانية |
| تجربة الاستعادة | شهريًا وبعد ترحيل جوهري |
| اختبار فشل النسخة | تنبيه مسؤول النظام وعدم اعتبار النسخة مكتملة |

## إجراء التعافي المقترح عند وقوع حادث
1. إيقاف التغييرات والرفع إلى البيئة المتضررة بإجراء معتمد؛ تسجيل وقت الحادث والنطاق والمسؤول.
2. تحديد آخر نسخة مستقلة سليمة مع مفتاحها المتاح وبصمتها. عدم نسخ قاعدة تالفة فوق النسخة الوحيدة.
3. استعادة النسخة على قاعدة جديدة معزولة، لا تتصل بها تطبيقات المستخدمين. تحقق من سلامة المحتوى والترحيلات والقيود والصلاحيات، الملفات والتقارير. لا تستخدم مفاتيح JWT الأصلية في البيئة المستعادة؛ يلزم إبطال الجلسات وتدوير الأسرار قبل أي إعادة ربط للتطبيق وفق خطة معتمدة.
4. قياس زمن الاستعادة والفقد الفعلي، وفحص المستخدمين والمرفقات وموافقة المسؤولين عن الأمن والبيانات. لا تحويل حركة المستخدمين أو إعادة فتح البيئة دون اعتماد منفصل.
5. تسجيل نتيجة الاستعادة في سجل إجراءات التشغيل دون أي بيانات طبية أو كلمات مرور.

## ضبط التكلفة
- لا خدمة PostgreSQL إضافية دائمة، لا تخزين Railway جديد ولا جدول تشغيل مدفوع مضاف في هذه المرحلة.
- إعادة استخدام مهمة PostgreSQL CI الحالية بدلاً من إضافة مهمة مستقلة. استهلاك دقائق CI ومساحة مؤقتة ممكن؛ لا وعد بتكلفة صفرية.
- عند الموافقة على نسخ Staging الفعلية: تخزين مؤسسي مشفر مستقل مع ضوابط الوصول والاحتفاظ؛ مفتاح منفصل، وآلية تنبيه. لا نسخ حقيقية في GitHub أو دردشة أو تخزين شخصي غير معتمد. تقدير التكلفة بعد قياس حجم النسخة ومعدل التغير والتخزين.
- قبل تفعيل الجدولة: التحقق من أن قاعدة Staging اصطناعية بالكامل، إثبات التفويض والموقع الآمن للتخزين وإدارة المفاتيح، مراجعة الاستعادة المستقلة والإجراءات التشغيلية. Production: NO-GO.
